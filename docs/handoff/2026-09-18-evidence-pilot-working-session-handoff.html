4 · Review Lifecycle

Statuses — FeedbackStatus: PENDING → RETURNED | REVIEWED (REJECTED retired). ProjectStatus: CREATED → ASSIGNED → IN_PROGRESS → SUBMITTED_FOR_REVIEW ⇄ RETURNED → APPROVED → ARCHIVED.

Section assigned → V38 baseline row captured (insert-if-absent)
▼
Student edits → submits → new PENDING request + SUBMITTED snapshot (submitForReview())
▼
Instructor reviews (active + previous request loaded)
▼
Return for Revision → drafts published + BASELINE snapshot (returnReview()) → Student revises → resubmits (new round)
▼
Approve → approveReview() (no thread-closure gate) → APPROVED · Reject attempt → 409

Resubmission creates a new PENDING request (a new round); drafts are keyed [project, request, section] so nothing stale carries over. Stored REJECTED rows stay readable; the enum values remain for history.

4 · Luồng vòng đánh giá

Trạng thái — FeedbackStatus: PENDING → RETURNED | REVIEWED (REJECTED đã nghỉ hưu). ProjectStatus: CREATED → ASSIGNED → IN_PROGRESS → SUBMITTED_FOR_REVIEW ⇄ RETURNED → APPROVED → ARCHIVED.

Giao section → lưu dòng baseline V38 (chỉ thêm nếu chưa có)
▼
Học viên sửa → nộp → request PENDING mới + snapshot SUBMITTED (submitForReview())
▼
Giảng viên chấm (tải request hiện tại + vòng ngay trước)
▼
Trả lại để chỉnh sửa (Return for Revision) → xuất bản nháp + snapshot BASELINE (returnReview()) → học viên sửa → nộp lại (vòng mới)
▼
Phê duyệt (Approve) → approveReview() (không cần đóng thread) → APPROVED · Reject → 409

Nộp lại tạo request PENDING mới (vòng mới); nháp được khóa theo [project, request, section] nên không rò rỉ dữ liệu cũ. Các dòng REJECTED cũ vẫn đọc được; giá trị enum giữ lại cho lịch sử.

5 · Show Diff and Baseline Semantics

Invariant: the Instructor compares the current Student submission against the state of the work when it was last handed to the Student.

  • First cycle: initial handoff baseline (V38 row) vs first submitted version.
  • Later cycles: latest earlier RETURNED BASELINE (review_section_snapshots) vs current submitted version.
  • Resolver/API: FeedbackServiceImpl.getComparisonSource() served at GET /api/feedback-requests/{id}/comparison-source as ComparisonSourceDto. Empty text is a valid baseline; row absence means unavailable.
  • Frontend: useInstructorReview fetches the source; wordDiff diffs normalized sources; Preview gates diff rendering and falls back to full-span display only.
  • Legacy fallback: no baseline → honest "comparison baseline unavailable", never invented data.
  • Why the old way was wrong: it diffed BASELINE vs SUBMITTED rows on the same request, but the backend writes BASELINE on the returned request and SUBMITTED on the new one — request A diffed a submission against itself, request B had no baseline.
  • Example (v4 → v5): ComparisonSourceTest.versionFourToFiveResolvesExactSourceStrings pins exact changed strings highlighted; truncation yields ranges: [], never guessed highlights.

5 · Show Diff và ngữ nghĩa baseline

Bất biến: giảng viên so sánh bản nộp hiện tại của học viên với trạng thái bài làm tại thời điểm bàn giao gần nhất cho học viên.

  • Vòng đầu: baseline bàn giao ban đầu (dòng V38) so với bản nộp đầu tiên.
  • Các vòng sau: BASELINE RETURNED gần nhất (review_section_snapshots) so với bản nộp hiện tại.
  • Phân giải/API: FeedbackServiceImpl.getComparisonSource() tại GET /api/feedback-requests/{id}/comparison-source, trả về ComparisonSourceDto. Chuỗi rỗng là baseline hợp lệ; không có dòng nghĩa là không khả dụng.
  • Frontend: useInstructorReview tải comparison source; wordDiff diff trên chuỗi đã chuẩn hóa; Preview chặn render diff khi không ánh xạ được.
  • Dự án cũ: không baseline → trạng thái "không có baseline" trung thực, không bao giờ bịa dữ liệu.
  • Vì sao cách cũ sai: nó diff hai dòng BASELINE/SUBMITTED trên cùng request, trong khi backend ghi BASELINE ở request bị trả và SUBMITTED ở request mới — request A diff bản nộp với chính nó, request B không có baseline.
  • Ví dụ (v4 → v5): ComparisonSourceTest.versionFourToFiveResolvesExactSourceStrings chốt đúng chuỗi thay đổi được highlight; khi cắt ngắn trả về ranges: [], không đoán mò.

6 · Instructor Feedback Data Flow

Editor selection (selection.main.from/to) or Preview selection (span map / structural zip)
▼
Canonical range + contentVersion + SHA-256 fingerprint → feedback draft
▼
POST /feedback-requests/{id}/feedback or PATCH /instructor-feedback/{id}
▼
FeedbackAnchorService.initialize() validates (400 otherwise) → anchor_json {original + current}
▼
Response DTO → mergeThread() → FeedbackCard / editor highlight
  • Whole-section: null anchor → SECTION projection ("Whole section").
  • Passage: anchored range with "Line N" / "Lines a–b" label via selectionLines.
  • Edit: draft seeded from the stored original passage, never the live position.
  • Reselection: Change passage → adjust mode → FAB "Use this passage" writes draft only; Update persists (same id), Cancel discards; Remove drafts whole-section.
  • Attachments: project-library picker (max 5), backend clones bytes; strip under the message with per-thumbnail remove.
  • Round ownership: create requires the latest PENDING/RETURNED request in submitted view; history is read-only.

7 · Overlapping Feedback

Example: Feedback A covers "The man has hooked a fish" (0–24); Feedback B covers "fish" (20–24). Both save independently. The composer shows a non-blocking notice (stronger wording for exact duplicates) with a link to the first overlapping item. Editor highlights (cm-feedback-range[data-feedback-id]) all render; clicking one selects the first match deterministically. Automatic merge/split was rejected: it would destroy authorship and independent lifecycles.

7 · Phản hồi trùng lặp (overlap)

Ví dụ: phản hồi A bao "The man has hooked a fish" (0–24); phản hồi B bao "fish" (20–24). Cả hai đều lưu độc lập. Composer hiện cảnh báo không chặn (mạnh hơn nếu trùng khít) kèm link tới mục đầu tiên. Mọi highlight editor (cm-feedback-range[data-feedback-id]) đều render; click chọn mục đầu tiên một cách xác định. Tự động gộp/tách bị từ chối: nó phá vỡ quyền tác giả và vòng đời độc lập.

9 · Instructor Review Workspace

Active request + immediately previous one load via reviewRounds.js (previousRequest) — never full history. Feedback tab: active-round threads, auto-arm composer, inline edit, overlap notices, attachments. History tab: previous-round cards read-only (drafts excluded). Highlights show ATTACHED/MODIFIED; DETACHED shows the struck-through original on the card. Show Diff resolves server-side. Return publishes drafts + writes BASELINE; Approve has no thread gate; Reject is a 409. Preview selections arm the canonical contract; unmappable content gets the honest banner.

9 · Workspace giảng viên

Tải request hiện tại + vòng ngay trước qua reviewRounds.js (previousRequest) — không bao giờ tải toàn bộ lịch sử. Tab Feedback: thread vòng hiện tại, composer tự arm, sửa inline, cảnh báo overlap, tệp đính kèm. Tab History: thẻ vòng trước chỉ đọc (loại nháp). Highlight hiển thị ATTACHED/MODIFIED; DETACHED hiện đoạn gốc gạch ngang trên thẻ. Show Diff phân giải ở server. Return xuất bản nháp + ghi BASELINE; Approve không cần đóng thread; Reject trả 409. Vùng chọn Preview arm đúng hợp đồng chuẩn; nội dung không ánh xạ được hiện banner trung thực.

10 · Feedback History

"Previous round" = nearest earlier request in orderedRequests. All its published section cards show (multi-card, newest first) through the shared read-only FeedbackCard. N-2 and older rounds are never fetched (asserted via feedbackCalls); deep links fetch one thread on demand. Flattening was rejected: it destroys round semantics and duplicates History's scoped job.

10 · Lịch sử phản hồi

"Vòng trước" = request gần nhất trước đó trong orderedRequests. Mọi thẻ đã xuất bản của vòng đó cho section hiện tại đều hiển thị (nhiều thẻ, mới nhất trước) qua FeedbackCard chỉ đọc dùng chung. Các vòng N-2 trở về trước không bao giờ được tải (đã assert qua feedbackCalls); deep link tải một thread khi cần. Gộp phẳng bị từ chối: nó phá ngữ nghĩa vòng và trùng việc của History.
